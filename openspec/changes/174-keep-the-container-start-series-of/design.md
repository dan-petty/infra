# Design

## Decisions

- **Add one name to the includeMetrics list of clusterMetrics.kube-state-metrics in the values template.**: The list at `helm/k8s-monitoring/values.yaml:35:includeMetrics:` already holds 20 kube-state-metrics names in this form, and the chart passes this field to the scrape of the collector that it configures, so one entry needs no template, flag or extra argument.
- **Read the new name in the rendered Alloy configuration of the alloy-metrics collector, and not in the arguments of the kube-state-metrics Deployment.**: The block of `helm/k8s-monitoring/values.yaml:13:clusterMetrics:` names `helm/k8s-monitoring/values.yaml:15:collector: alloy-metrics` and gives its kube-state-metrics entry `helm/k8s-monitoring/values.yaml:33:discoveryType: service`, while the Deployment settings are the block of `helm/k8s-monitoring/values.yaml:165:telemetryServices:`, so the tuning filters the scrape and the Deployment gets no metric name.
- **Set no metric allowlist flag on the kube-state-metrics Deployment.**: `helm/k8s-monitoring/values.yaml:171:metricLabelsAllowlist:` is the only metric setting of the Deployment block and it selects labels, not metrics, so kube-state-metrics exposes its series and the collector tuning is the only filter.
- **Place the new name directly after the kube_pod_container_status_waiting entry.**: The list groups the container series together, so a reader finds the container start gauge next to the running, ready, terminated and waiting gauges at `helm/k8s-monitoring/values.yaml:54:- kube_pod_container_status_waiting`.
- **Prove the entry with the shared K8s validation of the repository, run by a person on a workstation.**: `helm`, `kustomize` and `kubeconform` are NOT_IN_RUNNER, so no command of the implementation pod renders a Helm chart; the K8s check of the repository is the shared script of `README.md:288:| K8s |`.
- **Change no file of the test chart of the k8s-monitoring values template.**: The shared check renders the test chart with the values template under the name of its one dependency at `helm/k8s-monitoring/test-chart/Chart.yaml:5:- name: k8s-monitoring`, and the chart has no tests folder, so the entry reaches the render without a new case file or chart value.
- **Carry a spec delta for the new capability k8s-monitoring-values.**: The values template is a config file that a consumer observes, and the purposes of `ci-check-names` and `pr-title-scopes` show that no capability of the project describes a Helm values template.
- **State the requirement with the one scenario that runs the shared script with RENDERED set and searches the rendered objects for the name.**: This repository holds no `src` package, as `list_files` of the root shows, so no behavior group can cover a scenario that names no repository code; a scenario that names `scripts/k8s-validate.sh` and its command needs no behavior test. The exit status and the printed line of the script are the same before and after the change, so only the search of the rendered Alloy configuration can fail when the entry is missing.
- **Leave the post-release proof of the series to a person, and record it in no spec scenario.**: A series in the Prometheus of a consumer needs a release tag and a cluster, which no job of the repository reaches, and the second Done-when of the issue asks for that proof after the release. The tasks carry the proof as a Pending-a-person line under Workflow follow-up, which names the infra release and the move of the pinned infra tag of the consumer.
- **Keep the entry in the shared values template, and change no consumer file.**: A consumer loads this template first and its own values file after it. Helm replaces a list of an earlier values file, so a consumer file that sets its own `clusterMetrics.kube-state-metrics.metricsTuning.includeMetrics` list drops the entry; such a consumer must repeat each entry of this list. The plan names no file of a consumer repository.

## Rejected alternatives

- **Check the new name in the arguments of the rendered kube-state-metrics Deployment.**: `helm/k8s-monitoring/values.yaml:13:clusterMetrics:` names `helm/k8s-monitoring/values.yaml:15:collector: alloy-metrics`, so the includeMetrics list of its kube-state-metrics entry tunes the scrape of the collector, and the Deployment arguments come from the block of `helm/k8s-monitoring/values.yaml:165:telemetryServices:`, which holds no metric name.
- **Set useDefaultAllowList to false and list every kube-state-metrics metric in the values template.**: `helm/k8s-monitoring/values.yaml:35:includeMetrics:` adds names to the list that the chart builds; turning the default list off drops the names that the chart adds, so existing dashboards lose series.
- **Add a raw extra argument to the kube-state-metrics Deployment instead of the tuning entry.**: `helm/k8s-monitoring/values.yaml:169:collectorsExtra:` and `helm/k8s-monitoring/values.yaml:171:metricLabelsAllowlist:` show that the chart owns the Deployment settings, so a raw argument bypasses the tuning field and can collide with the configuration that the chart builds.
- **Add a helm unittest case file to the test chart that asserts the rendered configuration.**: `openspec/config.yaml:44` says that the scenario of a config file names a validator command or a live check as its proof, never a test that reads a value of the file. A case that matches the name in the rendered ConfigMap holds a value of the list, so each later edit of the list must also edit the case. The manual check reads the same render once and adds no lasting value test.
- **Use the K8s check of the devops gate as the verify of the values-file group.**: `helm` is NOT_IN_RUNNER, "No check, hook, test or job of the gate runs it", so that check renders no Helm chart, while the K8s check of the repository is the shared script of `README.md:288:| K8s |`.
